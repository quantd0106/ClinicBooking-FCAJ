# 5.5.4. Appointment Status History

## 1. Preserve an audit trail

`appointment_status_history` records how an appointment reached its current state. Keeping only `appointments.status` would lose the sequence of confirmation, completion, or cancellation, making business-event tracing and debugging harder.

The Prisma model is `AppointmentStatusHistory` in `prisma/schema.prisma`. Booking and transition writes are implemented by `AppointmentPersistenceService`.

## 2. Read the verified stored fields

| Prisma field | Stored meaning |
| --- | --- |
| `id` | History UUID, generated by default. |
| `appointmentId` | Reference to the appointment; mapped to `appointment_id`. |
| `oldStatus` | Previous appointment status, nullable; mapped to `old_status`. |
| `newStatus` | New appointment status; mapped to `new_status`. |
| `changedBy` | Actor's user ID, linked to `User`; mapped to `changed_by`. |
| `changedAt` | Timestamp defaulting to `now()`; mapped to `changed_at`. |
| `reason` | Nullable string, up to 500 characters. |

The model maps to `appointment_status_history`. `changedBy` is a user account reference, not a patient or doctor profile ID.

## 3. Create the initial PENDING history atomically

The booking transaction creates a PENDING appointment with nested history. This exact object-property excerpt comes from `bookAppointment()`; the appointment's other properties and surrounding create call are omitted:

```typescript
history: {
  create: {
    oldStatus: null,
    newStatus: AppointmentStatus.PENDING,
    changedBy: input.patientUserId,
  },
},
```

Creation has no previous state, so `oldStatus` is null. The actor is the authenticated patient's user ID. The schema supplies the history ID and timestamp; the initial reason is null.

Appointment creation and initial history must both succeed before the transaction commits. A rejected booking creates neither a partial appointment nor a successful-state history entry.

## 4. Append history for each valid transition

Within `transitionAppointment()`, the appointment status update and this exact history creation call share the same transaction:

```typescript
await transaction.appointmentStatusHistory.create({
  data: {
    appointmentId,
    oldStatus: appointment.status,
    newStatus,
    changedBy: actor.id,
    reason,
  },
});
```

History reflects the locked appointment's previous state and the authenticated actor. Confirmation and completion use the assigned DOCTOR or permitted ADMIN actor; cancellation uses the owning PATIENT, assigned DOCTOR, or ADMIN according to [5.5.2](../2-appointment-lifecycle/).

`CancelAppointmentDto` supports the optional reason string, up to 500 characters. The status-update DTO does not accept a reason field. When no reason is supplied, the nullable field remains null.

| Event | History old → new |
| --- | --- |
| Appointment created | null → PENDING |
| Doctor/Admin confirms | PENDING → CONFIRMED |
| Doctor/Admin completes | CONFIRMED → COMPLETED |
| Permitted cancellation | PENDING → CANCELLED or CONFIRMED → CANCELLED |

The application inserts a new history row rather than overwriting previous rows. If the transition is rejected or the transaction fails, it does not commit an audit entry claiming that change succeeded.

## 5. Inspect history through authorized detail access

`GET /api/v1/appointments/:id` and successful create/cancel/status responses include `history`, ordered by `changedAt` ascending. Each API history item contains `id`, `oldStatus`, `newStatus`, `changedBy`, `changedAt`, and `reason`; the detail response does not repeat `appointmentId` inside each item.

The paginated `/appointments/me` response omits history. Use authorized detail access for a timeline: own appointment for PATIENT, assigned appointment for DOCTOR, any appointment for ADMIN.

Check a successful creation and permitted transition, then compare the returned timeline with the local database history rows. Confirm that cancellation keeps the earlier PENDING/CONFIRMED entries and adds CANCELLED with the actor/reason. Rebooking creates a new appointment with its own initial history, preserving the cancelled appointment's timeline.

The inspected M4 tests cover initial history, lifecycle audit history, cancellation actor/reason, and one initial row for the winning concurrent booking. These are source-backed expectations for your local checks.
